# AGT-032 — Root-Cause the Post-Deploy OpenRouter Throttle Window

Status: Done
Depends On: None
Category: Investigation

## Description

Every fresh Cloud Run deploy this session (`AGT-021`/`022`/`029`/`030`'s redeploys) hit a ~1-3
minute window of `429 Too Many Requests` immediately after the new container started serving,
before queries started succeeding. The project owner asked for a real root cause, not a shrug —
specifically concerned this could be burning real money "without reason."

## Investigation

**Ruled out, with evidence, not assumption:**
- **Budget/quota exhaustion.** Checked `GET /api/v1/auth/key` and `GET /api/v1/credits` live
  during every throttle window: plenty of balance remaining each time ($9.9995 of $10 key cap,
  $4.998 of $5 account pool). Not the cause.
- **The key itself being blocked.** An isolated, single `curl` call to the exact same endpoint
  with the exact same key succeeded cleanly (`200 OK`, real cost registered) *during* the same
  window the app's own calls were getting `429`. Rules out an account-wide or IP-wide ban.
- **A retry-amplification bug in our own code.** Read `FallbackModel`'s source directly: on an
  API-level error it tries exactly the primary once, then the fallback once — the observed
  `FallbackExceptionGroup` messages consistently say "2 sub-exceptions," matching that exactly,
  not a multiplied retry storm. `PydanticAI`'s own `output_retries` (structured-output parsing
  retries, separate from API-error retries) don't re-trigger the whole `FallbackModel` chain —
  confirmed by the same "2 sub-exceptions" count holding steady regardless of each agent's
  configured `retries` value (Gatekeeper's default 1 vs. Writer/Verifier's 3).
- **Real financial cost from the failed attempts.** `429` responses are rejected by OpenRouter
  before any model processing happens — not billed. Confirmed via `AGT-030`'s own cost metric:
  exactly one cost sample per successfully *completed* `agent.run()`, never more than one per
  agent per query, across every observed run including the ones that eventually succeeded after
  several failed attempts. **No evidence of double-billing or wasted spend from this pattern.**

**A real, separate design gap found along the way (fixed, see Resolution):** the configured
fallback model (`nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free`) shares the *same* exhausted
daily free-tier quota the whole reason for switching to a paid primary was to escape. Any transient
hiccup on the paid primary was cascading into a guaranteed full failure, because the "fallback"
could never actually succeed today. This amplifies the *visible impact* of the throttle window
(every primary hiccup becomes a hard failure) without being its root cause.

**Root cause, corrected after further investigation (`AGT-031`'s debugging surfaced it
incidentally):** switching to native GCP Cloud Logging (needed to debug `AGT-031`'s own bug, since
this project's own OTLP log export is documented-flaky, `AGT-018`/`020`) revealed something the
Grafana-side logs had been silently dropping: the underlying `openai` Python SDK client (used by
PydanticAI under the hood) has **its own built-in retry-with-backoff on `429`**, visible as
`openai._base_client: Retrying request in 0.97 seconds (retry 2 of 2)` in the native logs. This
retries *within* a single logical call, underneath and invisible to both `FallbackModel`'s
"2 sub-exceptions" accounting and this project's own OTel tracing/logging — meaning the actual
request volume hitting OpenRouter during a throttle window was higher than anything this project's
own telemetry could see, explaining the burst far more directly than the original "provider
load-balancing" theory (still plausible as a contributing factor — two different upstream
providers, "Nebius" and "Novita", did appear across separate direct test calls — but no longer the
leading explanation).

This also reframes why switching the fallback model away from the exhausted free tier
(`AGT-032`'s one concrete fix) seemed to coincide with the throttle window becoming less visible
afterward: the `openai` SDK's own retry-with-backoff was likely absorbing most transient 429s on
its own already, with `FallbackModel`'s primary/fallback switch only needed for the cases that
outlasted that retry budget.
