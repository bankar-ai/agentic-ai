# AGT-021 — Per-Node Latency Instrumentation (Gatekeeper/Research/Writer/Verifier + MCP + LLM)

Status: Done (partial live verification — see Resolution)
Depends On: None
Category: Improvement

## Description

The Grafana dashboard restructure (2026-10-04) moved `enterprise-rag-platform`-specific latency
panels (LLM generation duration, RAG pipeline stage latency, ingestion duration) off the shared
dashboard because `agentic-ai` has no equivalent instrumentation of its own — those panels showed
"No data" for `agentic-ai` correctly, not as a bug, but because nothing in this codebase ever
emits spans or metrics under those names. This ticket is the actual equivalent: real latency
visibility into `agentic-ai`'s own pipeline (Gatekeeper → Research → Writer → Verifier, the MCP
tool-call round trip, the LLM call itself).

**Explicit scope boundary, agreed with the project owner:** this is latency/performance data
only. `app/core/tracing.py`'s `LangfuseTracer.trace_step()` already sends each node's *semantic*
content (route, reasoning, draft text, evidence count, grounded verdict) to Langfuse on every
live query — real, working, already deployed. `create_event()` is a point-in-time marker with no
span duration, so Langfuse currently has zero visibility into how long anything actually took.
This ticket fills exactly that gap and nothing else — no re-sending of content Langfuse already
has, no new Langfuse integration work.

## Resolution (2026-10-04)

Live verification surfaced two real, pre-existing issues in the deployed demo, unrelated to this
ticket's own code:

1. **Found and fixed:** `OPENROUTER_MODEL` on Cloud Run pointed at
   `nvidia/nemotron-3-nano-30b-a3b:free`, a slug that doesn't exist on OpenRouter (every call
   404'd, falling through to the configured fallback model). Corrected to the real slug
   `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free` and redeployed (`agentic-ai-00015-bfs`).
   This is a genuine, lasting fix — confirmed via Loki logs that the 404s stopped immediately
   after redeploy (every subsequent attempt got a clean 429, not a 404).
2. **Found, not fixable by retrying:** the OpenRouter API key has a **daily** free-model request
   cap (`free_model_daily_requests` via `/api/v1/auth/key`), and this session's testing (this
   ticket's own verification attempts plus everything before it today) had already burned
   through it (51/50 used) by the time of the last attempt. Every query from that point failed
   with 429 on both the primary and fallback free models, regardless of wait time — this is a
   quota reset (next UTC day), not a rate-limit backoff. Confirmed directly against OpenRouter's
   own key-status endpoint rather than inferred from repeated 429s.

Net effect: `gatekeeper_node`'s span wraps `grade_retrieval` correctly even when that call raises
(confirmed via the trace's `exception` event, type `pydantic_ai.exceptions.FallbackExceptionGroup`
and, earlier, `app.rag_client.retrieval.RagPlatformRetrievalError`) — both failure paths exercised
the span and metric code honestly, just not the success path for the three later nodes. This
should be re-verified once the OpenRouter free-tier quota resets; not reopening as a separate
ticket since the code is already reviewed/tested/deployed and the only gap is this one live
end-to-end check.

Not a correctness issue, not blocking anything — purely closing an observability gap the project
