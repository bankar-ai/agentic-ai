# AGT-056 — Secret-Leak Scanning on Generated Answers

Status: Done
Depends On: None
Category: Feature

## Description

Raised 2026-10-05 answering "are we checking each answer for secrets leak?" -- confirmed by code
audit: no. The Verifier's `grounded` check is a factual-accuracy check (does each claim trace back
to real retrieved evidence), not a safety check -- if a retrieved document happened to contain a
real secret (an API key, password, private key, etc. embedded in an ingested document) and the
Writer quoted it accurately, the Verifier would call that "grounded" and let it through, since
grounded only means "supported by evidence," not "safe to show."

## Acceptance Criteria

- [x] A secret-pattern scanner (`app/core/secret_scan.py`) covering common, well-known secret
      formats: AWS access keys, GitHub tokens, Slack tokens, private-key PEM headers, JWTs,
      generic `Bearer`/API-key-shaped strings
- [x] Applied to the final answer in both `/query` and `/query/direct`, before it's sent to the
      caller -- a detected secret overrides the result to refused (same `refused: true`/
      `final_answer: null` shape the Verifier's own rejection already uses), not a partial/
      redacted answer (safer and simpler to reason about than trying to redact reliably)
- [x] Tests: each covered secret pattern is actually caught; a normal answer with no secrets
      passes through unaffected
- [x] Deployed; verified by unit tests + router-level tests with mocked secret-containing
      results (see Resolution for why a real live secret couldn't be forced through genuine
      retrieved content)

## Notes

Pattern-based, not exhaustive -- will not catch a secret format it doesn't recognize, or one
disguised/split across the text. A real secret-scanning library (e.g. `detect-secrets`) would be
more thorough but is a new dependency; starting with the well-known-format patterns most likely to
appear in practice (API keys, tokens) is the proportionate first step, matching this project's
established pattern of scoped, low-risk fixes over large new dependencies.

## Resolution (2026-10-05)

Implemented exactly as scoped. Notable side effect while writing tests: realistic-looking
fixtures (even synthetic, non-functional ones) tripped both this project's own `gitleaks`
pre-commit hook and GitHub's server-side push protection -- correctly, since a secret-shaped
string is indistinguishable from a real leaked credential by shape alone, which is exactly the
point of both scanners and of this feature. Fixtures rebuilt via runtime string concatenation/
f-strings so the real shape still reaches the regex under test without a matching contiguous
literal ever existing in the source text. Deployed as part of commit `fdbb912` on `main`,
revision `agentic-ai-00041-gg6`.

**Not live-verified against a real secret leak** -- the only realistic way to trigger this live
would be an ingested document that actually contains a real-shaped secret, which none of the
project owner's real documents do (confirmed: all six are ordinary personal/safety documents).
Confidence comes from unit tests on the scanner itself and router-level tests with a mocked
secret-containing result confirming the override-to-refused path fires correctly end to end.
