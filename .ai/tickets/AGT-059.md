# AGT-059 — Database-Level Multi-Tenant Isolation (Row-Level Security)

Status: Backlog
Depends On: AGT-041, AGT-051
Category: Feature

## Description

Raised 2026-10-05: "hope we have RLS for multi-tenant leak stoppage?" Audited every query in
`app/core/query_cache.py` and `app/core/session_store.py` -- **confirmed no active leak today**,
every query correctly includes `WHERE user_id = $1`. But isolation is **application-level only**:
nothing at the database layer would stop a future query that forgot that clause, and the
connection uses one shared Postgres role (`neondb_owner`) for every user -- there is no per-tenant
database identity backing the isolation, just code discipline.

## Acceptance Criteria

- [ ] Postgres Row-Level Security enabled on both `query_history` and `user_sessions`: a policy
      restricting visible/writable rows to `user_id = current_setting('app.current_user_id', true)`
- [ ] `FORCE ROW LEVEL SECURITY` also set on both tables -- without it, RLS policies are silently
      bypassed for the table owner role, which is exactly the role this app connects as
      (`neondb_owner`), making the policy cosmetic rather than enforced
- [ ] Every query path sets `app.current_user_id` via `set_config(..., true)` (transaction-local)
      immediately before the actual query, in the same transaction -- `QueryCache`/`SessionStore`
      refactored to acquire a connection and open an explicit transaction per call rather than
      using the pool's bare `execute`/`fetchrow`/`fetchval`
- [ ] Fail-closed by design: a query that somehow runs without setting the session variable sees
      zero rows (`current_setting(..., true)` returns `NULL` when unset, and `user_id = NULL` is
      never true), not every user's rows
- [ ] Tests: a query scoped to one user cannot see another user's row even when (deliberately, in
      a test) the application-level `WHERE` clause is bypassed -- the point of this ticket is a
      defense that holds even when the code forgets, so the test should prove that, not just
      re-confirm the existing `WHERE` clause works
- [ ] Deployed and verified against the live database

## Notes

Defense-in-depth, not a fix for an active bug -- the application-level scoping already prevents
any leak today. This closes the gap where a *future* query (a new feature, a refactor, a mistake)
could otherwise leak across tenants with nothing at the database layer to catch it.
