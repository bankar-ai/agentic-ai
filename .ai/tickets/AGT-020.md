# AGT-020 — Logs + Metrics Export to Grafana Cloud

Status: Done
Depends On: None
Category: Improvement

## Description

`AGT-018` wired up traces only, with logs and metrics explicitly scoped out as optional stretch
goals. The project owner reviewed the live dashboard afterward and asked for both — the
dashboard's "Log volume by level"/"All recent logs" panels show "No data" for `agentic-ai` (no
logging exporter exists at all yet), and latency-style panels either show nothing or only
`enterprise-rag-platform`'s own data for `agentic-ai`'s traffic.

## Acceptance Criteria

- [ ] `app/core/logging_config.py` (new), mirroring `enterprise-rag-platform/app/core/
      logging_config.py`'s exact pattern — verify against the installed `opentelemetry-sdk`
      packages, don't assume the sibling repo's API still matches: a `TraceIdFilter` injecting
      the active span's trace ID into every log record, an OTLP `LoggingHandler` exporting via
      the same `OTEL_EXPORTER_OTLP_*` env vars `app/core/telemetry.py` already reads. Called once
      from `app/main.py` at startup, wrapped in try/except (same never-load-bearing stance as
      traces) — stdout logging must keep working even if OTLP export setup fails
- [ ] `app/core/telemetry.py` extended with metrics: a `MeterProvider` + push-based
      `PeriodicExportingMetricReader` over OTLP (no local Prometheus reader — this project has no
      `/metrics` endpoint and no local-dev collector to pull from, unlike
      `enterprise-rag-platform`'s dual-export setup)
- [ ] `new opentelemetry-exporter-otlp` sub-packages this needs (`_log_exporter`,
      `metric_exporter`) are already pulled in transitively by the `opentelemetry-exporter-otlp`
      dependency `AGT-018` added — confirm, don't assume, before adding anything new to
      `pyproject.toml`
- [ ] Same `_NoExtractPropagator` fix from `AGT-018` still applies here too (it's process-global,
      set once) — don't accidentally reintroduce `CompositePropagator([])` or any other variant
      that re-extracts Cloud Run's injected `traceparent`
- [ ] Cloud Run redeployed; live-verified (not just "the code looks right"):
      - A real log line visible via Grafana's Loki Explore / the dashboard's log panels,
        filtered by `service_name="agentic-ai"`
      - At least one real metric series visible via the dashboard's latency panels (or Prometheus
        Explore), for `agentic-ai` traffic specifically, not just `enterprise-rag-platform`'s
- [ ] `gcp-deployment-tracker.md` updated to reflect logs/metrics now exporting, alongside the
      existing traces entry

## Notes

Not a correctness issue — `agentic-ai` worked fine before this, and still would without it. This
is purely an observability-completeness ask from the project owner after seeing the live
dashboard's other panels (which are `enterprise-rag-platform`-specific — ingestion jobs, retrieval
eval, VM/docling/Modal health checks — and were never going to show `agentic-ai` data regardless
of this ticket; that's expected, not something this ticket tries to fix).

**Resolved (2026-10-04):** `app/core/logging_config.py` added (mirrors `enterprise-rag-platform`'s
pattern exactly — `TraceIdFilter` + OTLP `LoggingHandler`), and `app/core/telemetry.py` extended
with a `MeterProvider` + push-based `PeriodicExportingMetricReader`. No new dependencies needed —
confirmed the `_log_exporter`/`metric_exporter` sub-packages were already present transitively
from `AGT-018`'s `opentelemetry-exporter-otlp` dependency before writing any code.

**A real regression found deploying this, diagnosed rather than hand-waved:** right after this
redeploy, trace export (which `AGT-018` had already fixed and live-verified) started failing
again with the identical `Read timed out. (read timeout=0)` signature — but logs and metrics,
deployed in the *same* redeploy, worked immediately (confirmed via direct Loki and Prometheus
API queries: real log lines and a real `http_server_duration_milliseconds_count` series, both
tagged `service_name="agentic-ai"`, both genuine data not just "no error"). Same container
instance, same OTLP-over-HTTP export code path (`opentelemetry/exporter/otlp/common/http.py`),
two signal types succeeding and one failing pointed at payload size: `FastAPIInstrumentor` emits
several attribute-heavy spans per request (headers, URLs, nested ASGI send events), producing a
materially larger POST body per batch than log lines or metric points — consistent with a
payload-size-sensitive quirk in Cloud Run's gVisor network sandbox (the same general class of
issue as the earlier "read timeout=0" bug, just triggered by size this time, not absence of an
explicit timeout). Fixed by setting `BatchSpanProcessor(max_export_batch_size=1,
export_timeout_millis=30000)` — smaller individual export payloads. Live-verified after redeploy:
zero `read timed out` errors in Cloud Run logs across three real requests, and fresh Tempo traces
showing `rootServiceName: "agentic-ai"` for all three.

All three signals (traces, logs, metrics) now confirmed live via direct API queries against
Grafana Cloud's own backends (Tempo, Loki, Prometheus) — not inferred from the absence of error
logs.

**Metrics export flakiness: reduced, not eliminated — stated honestly, not overclaimed.** A few
hours after the above, the project owner spotted fresh `Failed to export metrics batch... read
timeout=0` errors live on the dashboard. Investigated: `PeriodicExportingMetricReader` has no
`max_export_batch_size` equivalent to the fix that resolved trace export (it exports every
current series each interval, not in configurable chunks), so the same lever wasn't available.
Added `export_timeout_millis=30000` as the one defensive option that does exist. Redeployed and
checked a fresh window: 1 metrics export error (down from consistent failures before), 0 span
errors, and confirmed via a direct Prometheus query that real metric data still landed
(`http_server_duration_milliseconds_count` matched the exact number of test requests sent)
despite that one failed attempt — periodic retries mean an occasional failure doesn't mean data
is lost, just delayed to the next interval. This is accepted as the same known Cloud Run sandbox
flakiness already documented for traces/logs, now also affecting metrics at a lower rate — not
claimed as fully solved, because it isn't.

**Dashboard structure — tried two approaches, settled on reverting, 2026-10-04 (separate from this
ticket's own scope, documented here since it directly followed from seeing this ticket's panels
live):** first split `enterprise-rag-platform`-specific panels onto a second dashboard so the
`$service_name` picker would behave correctly per-panel. Then, asked whether a single dashboard
could show/hide panels per selected service instead — tested directly against this Grafana Cloud
instance (version 13.3.0) by adding a `conditionalRendering` block to one panel and rendering the
dashboard via Grafana's own render API with each service value selected; the panel stayed visible
in both cases, confirming the attempted schema isn't recognized the way guessed. Reverted that
experiment cleanly (confirmed via read-back: no leftover experimental config).

**Final decision: reverted the whole restructure.** The two-dashboard split, while technically
working, was confusing in practice (navigating between two pages to see one project's full
picture) — the project owner asked for the original single dashboard back, with `agentic-ai`
metrics simply included in it rather than split out. Restored the dashboard to its exact
pre-restructuring 20-panel state from a saved snapshot (confirmed via read-back), deleted the
now-redundant `enterprise-rag-platform -- Service Detail` dashboard (its JSON kept locally).
`agentic-ai` remains in the `service_name` picker, and the genuinely cross-project panels
(traces, logs, HTTP latency) already show real `agentic-ai` data when selected — that part was
never undone. The `enterprise-rag-platform`-specific panels simply always show that project's own
data regardless of selection, exactly as they did before any of today's dashboard work — accepted
as the simpler, less confusing tradeoff.
