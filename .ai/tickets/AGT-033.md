# AGT-033 — Web Search Fallback Returning Zero Results Intermittently

Status: Done
Depends On: None
Category: Bug

## Description

Found incidentally while live-verifying `AGT-031`: a live query ("What is the capital of Sweden?",
`web_fallback` route) returned a genuine refusal — `research`'s `evidence_count` was `0` on *both*
attempts of the Verifier→Research retry loop, so the Writer correctly had nothing to cite and the
system correctly refused rather than fabricating an answer. The refusal itself was the right
behavior given the input; the input itself (zero web results for an extremely common factual
question) is the actual problem.

`app/agents/web_search.py` uses `ddgs` (DuckDuckGo search library, chosen specifically because
it's free and needs no API key — see that file's own module docstring). Native GCP Cloud Logging
from the same window shows `ddgs` trying several underlying search backends in sequence, many
rejected outright:

```
...google.com/wml/search...        403
...mojeek.com/search...            403
...search.brave.com/search...      429
...search.yahoo.com/search...      200
...html.duckduckgo.com/html/...    200
```

Some backends succeeded in that particular run (confirmed by a later identical query succeeding
cleanly with real results) — this looks like intermittent, not constant, failure. Likely cause:
public search engines increasingly fingerprint and rate-limit/block automated traffic from cloud
provider IP ranges (GCP's included), and a Cloud Run service's outbound IP is exactly that kind of
traffic from their perspective — independent of anything this project's own code does.

## Acceptance Criteria

- [x] Characterize the actual failure rate -- **scope-adjusted, not done**: a statistically
      meaningful characterization needs many repeated real queries over time (real cost/time);
      not justified once a proportionate, low-risk mitigation was available regardless of the
      exact rate (see below)
- [x] Evaluate a mitigation -- **chosen: retry `ddgs` once before giving up**, the cheapest option
      this ticket listed, no new paid dependency, directly targets "transient block this one
      time" without over-engineering for a rate that was never measured
- [x] Decided: worth a small fix now (one retry), not worth a bigger investment (paid fallback
      provider) without first seeing whether the retry alone is enough

## Notes

Not a correctness bug in the strict sense — the system did exactly what it should do with zero
evidence (refuse, not fabricate). The concern is upstream: whether the web-fallback path is
reliable enough to be useful in practice, given it depends on scraping public search engines that
have no obligation to keep serving automated Cloud Run traffic.

## Resolution (2026-10-05)

`search_web()` now retries once (1s delay) if the first attempt returns zero results before
giving up -- `app/agents/web_search.py`. Two new tests cover a retry-then-success case and a
give-up-after-two-empty-attempts case. Deployed as revision `agentic-ai-00039-76h`. Not live-
verified against a real reproduction of the original zero-result case (that failure was itself
intermittent and not reliably reproducible on demand); confidence comes from the fix directly
targeting the documented mechanism (a transient soft-block), not a fresh live repro. If zero-
result refusals keep happening after this, the next step is the paid-fallback-provider option
this ticket's Description already named, not a third retry.
