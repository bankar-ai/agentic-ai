# AGT-013 — Multi-Tenant Auth: Per-User RAG-Platform Tokens End-to-End

Status: Backlog
Depends On: None
Category: Improvement

## Description

Today `agentic-ai` is single-tenant: every query, from every visitor, uses one fixed service
account (`agentic-ai-service@example.com`) baked into `.env`, so everyone sees the same documents
regardless of who's asking. This surfaced as a real gap: there's no end-user login concept at all,
and reusing `enterprise-rag-platform`'s own login (rather than building a second identity system)
is both the simplest and most honest design — `agentic-ai` never owns passwords, it only forwards
an already-issued RAG-platform access token.

**Additive, not a breaking change**: when no token is supplied, behavior is unchanged (the fixed
service account still works, so local dev / CI / the existing smoke-test flow keep working as-is).

The identity has to flow further than just the API layer: Gatekeeper's exploratory search *and*
Research's MCP subprocess call both hit the RAG platform's retrieval API, and both need to act as
the calling user, not the fixed service account, for multi-tenancy to be real rather than
cosmetic.

## Acceptance Criteria

- [ ] `POST /query` accepts an optional `Authorization: Bearer <token>` header
- [ ] A new lightweight auth adapter (alongside `RagPlatformAuth`) that wraps an already-issued
      access token and satisfies the same interface `RagPlatformRetrievalClient` expects
      (`get_access_token()`), without knowing a password — a token that turns out to be
      expired/invalid surfaces as a clear 401 from `agentic-ai`, not a confusing deep failure
      inside the graph
- [ ] `get_graph()` builds its retrieval client from the per-request token when present, the
      configured service account when absent
- [ ] The MCP subprocess (`app/mcp_server/server.py`) receives the active identity per-call (env
      var set at spawn time by the Research agent) rather than only ever reading its own
      `RAG_PLATFORM_EMAIL`/`PASSWORD` from its own `.env`
- [ ] Gatekeeper's exploratory search (`app/agents/gatekeeper.py`) uses the same per-request
      identity, not a separately-configured one — both retrieval calls for one query must see the
      same user's documents
- [ ] Tests: unauthenticated request still works (fixed service account path unchanged), a
      supplied token is genuinely used for retrieval (not ignored), an expired/invalid token
      produces a clear 401 rather than a graph crash
