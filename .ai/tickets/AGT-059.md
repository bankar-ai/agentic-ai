# AGT-059 — Database-Level Multi-Tenant Isolation (Row-Level Security)

Status: Done
Depends On: AGT-041, AGT-051
Category: Feature

## Description

Raised 2026-10-05: "hope we have RLS for multi-tenant leak stoppage?" Audited every query in
`app/core/query_cache.py` and `app/core/session_store.py` -- **confirmed no active leak today**,
every query correctly includes `WHERE user_id = $1`. But isolation is **application-level only**:
nothing at the database layer would stop a future query that forgot that clause, and the
connection uses one shared Postgres role (`neondb_owner`) for every user -- there is no per-tenant
database identity backing the isolation, just code discipline.

## Acceptance Criteria

- [x] Postgres Row-Level Security enabled on both `query_history` and `user_sessions`: a policy
      restricting visible/writable rows to `user_id = current_setting('app.current_user_id', true)`
- [x] `FORCE ROW LEVEL SECURITY` also set on both tables -- **this alone turned out to be
      insufficient**, see Resolution for the real bug this surfaced and how it was fixed
- [x] Every query path sets `app.current_user_id` via `set_config(..., true)` (transaction-local)
      immediately before the actual query, in the same transaction -- `QueryCache`/`SessionStore`
      refactored to acquire a connection and open an explicit transaction per call rather than
      using the pool's bare `execute`/`fetchrow`/`fetchval`
- [x] Fail-closed by design: a query that somehow runs without setting the session variable sees
      zero rows (`current_setting(..., true)` returns `NULL` when unset, and `user_id = NULL` is
      never true), not every user's rows -- **live-confirmed**, not just designed that way
- [x] Isolation proven to hold independent of the application-level `WHERE` clause -- **not a unit
      test** (a fake pool can't exercise real RLS enforcement), done instead as a live test
      against the real database using the actual application classes, see Resolution
- [x] Deployed and **verified against the live database with unusual rigor** -- found and fixed a
      real bug along the way, see Resolution

## Notes

Defense-in-depth, not a fix for an active bug -- the application-level scoping already prevents
any leak today. This closes the gap where a *future* query (a new feature, a refactor, a mistake)
could otherwise leak across tenants with nothing at the database layer to catch it.

## Resolution (2026-10-05)

**A real bug found during live verification, not just a successful deploy.** First deploy of
`ENABLE`/`FORCE ROW LEVEL SECURITY` + the policy looked correct (`pg_class` confirmed both flags
set), but a direct live test told a different story: querying as three different
`app.current_user_id` values (unset, the real user, a fake other user) all returned the exact
same 41 rows. **RLS was configured correctly and doing nothing.**

Root cause: `neondb_owner` -- the only role this app has ever connected as -- has
`rolbypassrls = true`. Confirmed directly: `SELECT rolbypassrls FROM pg_roles WHERE rolname =
current_user` returned `true`. This is Neon's default for a project's primary database role.
`FORCE ROW LEVEL SECURITY` specifically exists to make RLS apply to a table's *owner* -- but it
has no effect on a role with the `BYPASSRLS` attribute regardless of ownership or `FORCE`; that
attribute bypasses RLS everywhere, unconditionally. The acceptance criteria above (and the
original ticket) assumed `FORCE` was sufficient -- it is, for an ordinary owner role, but not for
one with this attribute, which is exactly what `neondb_owner` turned out to have.

**Fix**: created a dedicated, least-privilege role, `agentic_ai_app` (`NOBYPASSRLS`, confirmed:
`rolbypassrls = false`), granted exactly `SELECT`/`INSERT`/`UPDATE`/`DELETE` on the three tables
plus sequence usage, then transferred *ownership* of `query_history`/`user_sessions`/
`rate_limit_events` to it (needed so the app's own schema-init DDL -- `CREATE TABLE IF NOT
EXISTS`, `ALTER TABLE ... ENABLE/FORCE ROW LEVEL SECURITY`, `CREATE POLICY` -- can still run
without granting the app's runtime role any ALTER/ownership-level privilege on the admin's
behalf; a non-bypassing *owner* is still genuinely subject to `FORCE ROW LEVEL SECURITY`, so this
satisfies both "the app can manage its own schema" and "the app is actually bound by RLS" at
once). `neondb_owner` is retained for admin/manual work only -- deliberately never put back into
the app's own `DATABASE_URL`. Updated `C:\Users\Pankaj\.credentials\agentic-ai-credentials.md`
and Secret Manager (`agentic-ai-database-url`, version 2) accordingly.

**Re-verified after the fix, against the real database, using the real `QueryCache`/`SessionStore`
classes (not just raw SQL)**:
- Unscoped `count(*)`: `0` (fail-closed, confirmed, not just designed)
- Scoped to the real user id: `41` (all their real rows)
- Scoped to a fake, never-used user id: `0` -- genuine cross-tenant isolation, not just "the
  policy exists"
- A real `INSERT` + immediate scoped read-back under the new role: succeeded and visible,
  confirming writes still work, not just that reads got more restrictive
- The real app's own `get_query_cache`/`get_session_store`/`QueryCache.lookup`/`list_recent`
  functions, run directly against the new role, behaved identically to the raw-SQL test

Redeployed as revision `agentic-ai-00042-dsf` with the new connection string. Confirmed the live
app still works end-to-end post-switch: a real rate-limit check against the real database
(`AGT-058`) correctly reflected prior activity immediately after the role swap, and direct
inspection of `query_history` confirmed real rows from live testing throughout this session are
intact and correctly attributed.

This is exactly the kind of gap this ticket set out to close -- a correctly-written policy that
silently did nothing, found only because live verification checked the actual behavior rather
than trusting the configuration.
