# AGT-019 — CI/CD: Deploy to Cloud Run on Merge to `main`

Status: Backlog
Depends On: None
Category: Improvement

## Description

Every deploy so far (`AGT-005`/`AGT-007`, and the AGT-008/009/011/012/016/017 redeploys) has been
a manual `gcloud run deploy agentic-ai --source . ...` run from a developer's own machine, logged
into their own `gcloud` session. There is no pipeline that deploys automatically when `main`
changes — the existing `.github/workflows/` only runs tests/lint (`AGT-002`'s Gitleaks + CI
backstop), nothing deploys.

## Acceptance Criteria

- [ ] New GitHub Actions workflow (e.g. `.github/workflows/deploy.yml`) triggered on push to
      `main`, running the exact `gcloud run deploy` command already documented in
      `gcp-deployment-tracker.md`'s "Redeploy" section (same flags, same secrets references) —
      not a reinvented deploy config
- [ ] GCP authentication for the workflow via **Workload Identity Federation**, not a long-lived
      service-account JSON key committed as a GitHub secret — WIF avoids a static credential that
      can leak and never expires; this is the one part of this ticket that provisions real GCP
      IAM resources (a Workload Identity Pool + Provider + service account binding) and **must be
      confirmed with the project owner before creating anything**, per this repo's own
      instructions on credential-sensitive and infra-affecting actions
- [ ] Existing test/lint CI job still runs and must pass before deploy (gate the deploy job on
      it, don't run them as unrelated parallel jobs)
- [ ] `gcp-deployment-tracker.md` updated: the "Redeploy" section now says deploys happen via CI
      on merge to `main`, with the manual command kept as a documented fallback, not deleted
- [ ] One real, observed successful run (a real merge to `main` triggers a real deploy) before
      calling this done — not just "the YAML looks right"

## Notes

**Status (2026-10-04): drafted, paused pending explicit confirmation.** The workflow itself
(`.github/workflows/ci.yml`'s new `deploy` job) is written and committed to `develop` only — not
merged to `main`, since it would show as a failing check on every `main` push until the secrets
below exist. It is genuinely incomplete without the project owner's go-ahead to create the real
GCP resources it needs:
- A Workload Identity Pool + OIDC provider trusting `token.actions.githubusercontent.com`
- A GCP service account with `roles/run.admin` (or similar) bound to this specific GitHub repo
- Three GitHub repo secrets: `GCP_WORKLOAD_IDENTITY_PROVIDER`, `GCP_DEPLOY_SERVICE_ACCOUNT`,
  `GRAFANA_OTLP_HEADERS`

**Why this needs a pause mid-implementation, not just a ticket beforehand:** setting up Workload
Identity Federation means creating a Workload Identity Pool, an OIDC provider trusting
`token.actions.githubusercontent.com`, and an IAM binding granting a GCP service account
`roles/run.admin` (or similar) to a specific GitHub repo — real, standing access from GitHub's
infrastructure into this GCP project. That is exactly the class of action this repo's own
guidance calls out for explicit confirmation first (credential-sensitive, affects shared/external
systems), so implementation should stop and ask before running any `gcloud iam` /
`gcloud workload-identity-pools` command, even though the ticket itself can be written and the
workflow YAML drafted without it.
