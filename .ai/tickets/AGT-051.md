# AGT-051 — Revisit Persistent Sessions / Refresh Tokens Now That a Database Exists

Status: Backlog
Depends On: AGT-041
Category: Feature

## Description

The "session will expire soon" warning (`AGT-026`) exists because `agentic-ai` deliberately has
no server-side session storage: `StaticTokenAuth` holds only the short-lived access/CSRF tokens
`enterprise-rag-platform` issues at login, with no way to silently refresh them. `AGT-013`/`AGT-026`
investigated true silent refresh and explicitly declined it: *"can't be done without a real
architecture change -- `agentic-ai`'s backend would have to start holding per-user refresh-token
state it doesn't have today."*

That blocker no longer fully applies. `AGT-041` gave `agentic-ai` its first real database
(dedicated Neon Postgres). Storing a refresh token server-side, scoped per user, is now a much
smaller lift than it was when "stand up a database just for this" was the alternative being
weighed against "live with the warning." Worth re-evaluating, not assuming the old answer still
holds now that the premise it was based on has changed.

**Not a bug** -- the current warning-plus-draft-preservation behavior is a previously made,
reasoned decision, not an oversight. This ticket is "should we revisit it," not "this is broken."

## Acceptance Criteria

- [ ] Re-evaluate: does `enterprise-rag-platform`'s own `/auth/login` response (or a separate
      endpoint) expose a refresh token `agentic-ai` could store and use? (Check against that
      platform's ERP-116 cookie+CSRF contract -- it may deliberately keep refresh tokens
      `httpOnly` and inaccessible to a server-side proxy like `agentic-ai`, which would reopen a
      different blocker than "no database")
- [ ] If feasible: design (brainstorming pass, likely architectural -- this changes the trust
      model, not just adds a UI nicety) a server-side refresh-token store in the new
      `query_history` database (or a separate table) and a silent-refresh flow
- [ ] If not feasible (e.g. the platform's tokens are genuinely not meant to be held by a
      third-party backend like this one): document why clearly, so this doesn't get re-asked
      without the answer being discoverable
- [ ] Decide and record the outcome either way -- this ticket's job is the investigation and
      decision, not necessarily the implementation

## Notes

Genuinely open -- unlike `AGT-026`'s original call, which was made when "no database" was a real
constraint, this one deserves a fresh look now that the constraint is gone. Still may land on "no"
for a different reason (e.g. `enterprise-rag-platform`'s own token design), but that should be
confirmed, not assumed.
