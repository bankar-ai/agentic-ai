# AGT-018 — Grafana Cloud Observability (Traces/Logs/Metrics)

Status: Done
Depends On: None
Category: Improvement

## Description

`enterprise-rag-platform` already has a working Grafana Cloud stack (`microstarfish1843`, free
tier: traces, logs, metrics via OTLP) and a dashboard ("AI Platforms — Service Observability")
*already built to be reusable across future portfolio projects* via a `service_name` picker —
see `D:\github-projects\gcp-deployment-tracker.md`'s "Observability" section. `agentic-ai` has
never been wired into it: no OTel traces, logs, or metrics leave the Cloud Run service today
beyond Langfuse's own LLM-call tracing (`app/core/tracing.py`, a separate, narrower concern).

This is a portfolio-consistency item flagged by the project owner (2026-10-03), not a
deployment blocker.

## Acceptance Criteria

- [ ] `app/core/telemetry.py` (new, mirroring `enterprise-rag-platform/app/core/telemetry.py`'s
      exact pattern — verify against the installed `opentelemetry-*` packages, don't assume the
      sibling repo's exact API still matches): `TracerProvider` + `BatchSpanProcessor` with an
      OTLP exporter selected by `OTEL_EXPORTER_OTLP_PROTOCOL` (`http/protobuf` for Grafana
      Cloud's gateway, `grpc` default for local dev against nothing in particular since this repo
      has no local Jaeger/collector setup)
- [ ] `FastAPIInstrumentor.instrument_app(app)` and `HTTPXClientInstrumentor().instrument()` in
      `app/main.py`'s startup — no `SQLAlchemyInstrumentor`/`RedisInstrumentor` needed, this
      project has no database
- [ ] Setup wrapped in try/except, logged and swallowed on failure — observability must never be
      able to prevent the app from starting or serving requests (same stance
      `enterprise-rag-platform`'s own `configure_telemetry` takes)
- [ ] New `OTEL_EXPORTER_OTLP_ENDPOINT`/`_PROTOCOL`/`_HEADERS`/`OTEL_SERVICE_NAME` env vars
      documented in `.env.example`, unset by default (matches local dev doing nothing rather than
      erroring without a collector)
- [ ] Cloud Run deploy updated with these env vars pointing at the existing Grafana Cloud stack,
      reusing the existing `rag-platform-vm-traces` API token (same Grafana account, scope
      already covers traces/logs/metrics) — no new Grafana resource created
- [ ] `agentic-ai` added to the existing dashboard's `service_name` **static** option list
      (Grafana Dashboard settings → Variables → `service_name` → Static options — the stack's
      `label_values()` doesn't auto-discover, per the tracker's existing note) once it starts
      sending data
- [ ] Live-verified: at least one real request's trace visible in Grafana Cloud's Tempo Explore,
      filtered by `service_name="agentic-ai"`
- [ ] `gcp-deployment-tracker.md`'s `agentic-ai` entry updated to note observability is wired in,
      matching the existing `enterprise-rag-platform` entry's format

## Notes

Logs via `app/core/logging_config.py`-equivalent (ERP-039's pattern) and metrics via
`app/core/telemetry.py`'s `PeriodicExportingMetricReader` (ERP-042's pattern) are both optional
stretch goals beyond this ticket's minimum — traces are the primary ask (observable request flow
through the Gatekeeper/Research/Writer/Verifier graph); add logs/metrics only if traces land
cleanly and time allows.

**Resolved (2026-10-04):** `app/core/telemetry.py` added (traces only — logs/metrics stretch
goals not picked up), wired into `app/main.py`. Reuses the existing `rag-platform-vm-traces`
Grafana Cloud API token and endpoint verbatim (same instance, same OTLP gateway) — no new
Grafana resource created. Cloud Run redeployed with the four `OTEL_*` env vars.

**A real bug found deploying this, not assumed away:** the first deploy's exporter failed every
export with `Read timed out. (read timeout=0)` against Grafana's OTLP gateway — some aspect of
Cloud Run's environment resolves `HttpOTLPSpanExporter()`'s default timeout to `0` rather than
its documented ~10s fallback. Fixed by passing `timeout=10` explicitly in
`_build_span_exporter()`. Confirmed via the Grafana HTTP API (Tempo's `/api/search`, same data
the dashboard's Explore view reads) that traces tagged `service.name=agentic-ai` now actually
arrive — not just that the exporter stopped logging errors.

`agentic-ai` added to the dashboard's `service_name` **static** options via the Grafana
dashboards API directly (`staticOptions` now `["self-hosted-rag-platform", "agentic-ai"]`) —
confirmed with a read-back after the update, not just a 200 on the write.
