# AGT-009 — Manage `get_graph()`'s Client Lifecycle

Status: Done
Depends On: None
Category: Lapse

## Description

`get_graph()` (`app/api/router.py`) rebuilds the Ollama model, an `httpx.AsyncClient`, the auth
client, and the retrieval client from scratch on every single `POST /query` request — and the
`httpx.AsyncClient` instances it creates (here, in `app/ui/app.py`, and in
`app/mcp_server/server.py`) are never explicitly closed. Flagged as a deferred Minor in the final
whole-branch review (`M-3`) and in `AGT-013`'s Task 13 ledger note. Fine for a low-traffic demo;
genuinely wasteful (a fresh TCP connection and a fresh RAG-platform login per query) for anything
with real concurrent traffic.

## Acceptance Criteria

- [ ] A shared, lazily-constructed (or FastAPI-lifespan-managed) `httpx.AsyncClient` reused across
      requests, properly closed on app shutdown
- [ ] `RagPlatformAuth`'s cached-token benefit actually realized across requests (currently reset
      every request since a fresh instance is built each time, defeating the point of its own
      token-caching design)
- [ ] Same treatment for `app/ui/app.py` and `app/mcp_server/server.py`'s client construction

## Notes

Category is **Lapse**, not Bug — the code works exactly as designed, the design just didn't
account for a high-request-volume case. Low priority unless/until real concurrent traffic is
expected (e.g. before a live interview demo with multiple testers hitting it at once).

**Resolved (2026-10-03):** `app/rag_client/shared_client.py`'s `get_shared_rag_platform_client()`
(`@lru_cache`) is now reused across every request in `get_graph()` (API) and
`_get_retrieval_client()` (UI), closed explicitly on FastAPI shutdown via a new `lifespan` in
`app/main.py`.

**A real concurrency hazard caught while implementing this, not assumed away:** the original
design (`StaticTokenAuth` mutating the shared `http_client`'s own cookie jar) would have been
unsafe to share across concurrent requests from *different users* — one jar, mutated per
request, leaking one user's session cookies into another's in-flight request. Fixed by removing
all cookie-jar reliance from `app/rag_client/auth.py`/`retrieval.py`: every auth value now
travels as an explicit per-request header/cookie string built fresh each call, so the shared
client holds only pooled connections, never per-caller state. Live-verified against the real RAG
platform after the refactor.

**Second acceptance criterion ("`RagPlatformAuth`'s cached-token benefit...") is now moot, not
skipped:** it assumed the pre-`AGT-006` architecture where `RagPlatformAuth` (the fixed service
account) ran on every request. Post-`AGT-006` there is no service-account fallback in the
per-request hot path at all — only `StaticTokenAuth` (a caller's own session, nothing to cache)
is used there. `RagPlatformAuth` now only runs on infrequent login calls
(`login_and_extract_session`) and the MCP server's own standalone-dev fallback, neither of which
is a per-request hot path needing this optimization.

Third criterion (`app/mcp_server/server.py`'s client): that subprocess is spawned fresh per
Research call already (one client per subprocess lifetime, not per-request reuse the way the
API/UI needed), so the fix there is "close it" rather than "share it" — done via a
`_close_retrieval_client()` call in a `try`/`finally` around `mcp_server.run_stdio_async()`. This
also resolves `AGT-012`'s item 3, which was the same gap in the same file.
