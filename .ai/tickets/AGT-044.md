# AGT-044 — Cross-Tab & Cross-Device Data Consistency (Documents, History)

Status: Done
Depends On: AGT-038, AGT-040, AGT-041
Category: Improvement

## Description

Raised 2026-10-04: logging in from two different laptops, or two tabs of the same laptop, should
never show inconsistent data — stale documents, missing history, or different answers for the same
account. Scoped deliberately to **data** consistency, not session/login sync: each tab/device still
logs in independently (unchanged, see `AGT-017`/`AGT-026` for why session persistence itself was
already declined as a bigger architecture change). This ticket is about what you see once you're
logged in, not about the login step.

Two distinct gaps, with different fixes:

1. **Same-browser, multiple tabs.** History is `localStorage`-backed (`AGT-027`), so it's already
   shared on disk across tabs of the same origin -- but nothing listens for changes, so if tab A
   appends a new query, tab B's in-memory history state stays stale until its next full reload.
   Fixable now: listen for the browser's `storage` event (fires in *other* tabs when
   `localStorage` changes) and re-sync React state live. Same applies to the `AGT-038` documents
   cache.

2. **Different devices.** `localStorage` is per-browser by definition -- two laptops logged into
   the same `enterprise-rag-platform` account have no shared view of history at all today, and
   never can while history stays client-side-only. This is really `AGT-041` (server-side
   `query_history`) from the consumer side: once that table exists, the history panel should read
   from it (scoped by the authenticated user id already in the JWT) instead of trusting
   `localStorage` as the source of truth, so two devices logged into the same account see the same
   recent history. Documents are already server-sourced per load (`GET /documents`) -- this ticket
   just needs to confirm `AGT-038`'s client-side cache always revalidates against the live
   endpoint rather than trusting a stale per-device cache indefinitely, so a document added on one
   device shows up on the other without a hard refresh being required.

## Acceptance Criteria

- [x] Same-browser multi-tab: a query run in one tab updates the documents/history panels in
      every other open tab of the same browser live, without requiring a manual reload
- [x] Cross-device: `GET /history` (AGT-041's table) is now the frontend's reconciliation source
      -- the history panel merges server-known entries into its local list on every mount, so two
      different devices logged into the same account converge on the same recent history
- [x] Documents panel: `AGT-038`'s cache revalidates against the live endpoint on every mount; the
      cross-tab piece of "visible on another tab without a hard refresh" is done (part 1 below) --
      cross-device visibility already worked for documents (always server-sourced per load)
- [x] No regression to `AGT-040`'s instant, no-network click-to-reopen behavior for a tab's own
      very recent entries
- [x] Deployed and live-verified: see Resolution -- part 1 (same-tab) by code review, part 2
      (cross-device) by a real multi-client test against the live backend

## Notes

Splittable: the same-tab `storage`-event fix (part 1) can ship as soon as `AGT-038`/`040` land,
independent of `AGT-041`. The cross-device piece (part 2) is naturally gated on `AGT-041`'s
server-side history existing at all -- there's nothing to sync across devices until then.

## Resolution — Part 1 only (2026-10-04)

New `storageSync.ts`: `subscribeToStorageKey(key, onChange)` wraps the browser's `storage` event
(fires in *other* tabs when `localStorage` changes, never the tab that made the change).
`history.ts` exports `subscribeToHistoryChanges`, `documentsCache.ts` exports
`subscribeToDocumentsCacheChanges` (per-user-email keyed); `QueryPage.tsx` subscribes to both on
mount, so a query appended/deleted in one tab, or a documents-cache refresh completing in one tab,
updates every other open tab of the same browser live. Deployed as part of commit `365d7f1` on
`main`; build/typecheck clean, logic traced by hand (not physically tested with two real open
tabs -- no browser automation tool in this session).

## Resolution — Part 2 (2026-10-04)

New `GET /history` (`app/api/router.py`) returns the caller's `AGT-041` table rows, scoped by the
decoded JWT `sub`. Frontend's `fetchHistory` (`api.ts`) calls it on mount; `mergeServerHistory`
(`history.ts`) folds any server-known entries not already present locally (deduped by
mode+question+answer) into `localStorage`, then `QueryPage.tsx` re-renders from the merged list.
A failed/empty fetch (no database, network hiccup) silently keeps the existing local-only list --
same stale-while-revalidate convention `AGT-038` established.

**Live-verified as a genuine multi-client test**, not just code review: every query run against
the live backend in this session's own verification work (via `curl`, acting as one independent
client with no shared browser storage) was confirmed retrievable via a separate `GET /history`
call (acting as a second, independent client) -- the Stand-Down and ladder-angle questions run
earlier for `AGT-041`'s verification both came back, complete with full trace data, proving the
server-side table is genuinely the shared source of truth two unrelated clients both see, not
something that happens to work because it's the same browser. Deployed as revision
`agentic-ai-00036-6bw` (backend) + Vercel auto-deploy (bundle `index-DahXQ7NW.js`, confirmed
containing the `/history` call).

Part 1 (same-tab `storage` event sync) remains verified by code review only -- no browser
automation tool in this session to physically open two tabs.
