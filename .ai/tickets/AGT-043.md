# AGT-043 — Verifier Self-Contradiction: Confirms a Claim Is Supported, Then Flags It Unsupported

Status: Done
Depends On: None
Category: Bug

## Description

Found 2026-10-04 while answering the project owner's question "is the Verifier doing its job
properly?" — reviewed the real two-rejection trace captured during `AGT-035`'s re-verification
rather than assuming it's fine. The second rejection round looks like sound judgment (correctly
flagging a genuine overgeneralization in the Writer's draft). The **first** rejection round
contains a real inconsistency:

```
"reasoning": "The document explicitly states 'No fall protection program'. However, the claim
  \"assign a person to inspect fall protection equipment before each use\" is not directly
  supported by the provided evidence...",
"unsupported_claims": [
  "However, the company currently has no fall protection program.",
  "assign a person to inspect fall protection equipment before each use"
]
```

The `reasoning` text explicitly confirms the document *does* state there's no fall protection
program (i.e. that claim **is** grounded) — but the same claim is then listed in
`unsupported_claims` anyway, forcing a retry (and eventually refusal) partly over a claim the
Verifier's own stated reasoning says is true. This isn't the system being "too strict" in a
principled way; it's the Verifier's structured output disagreeing with its own free-text
reasoning for the same claim.

Likely a prompt/output-parsing issue in `verify_answer()` (the LLM's structured `unsupported_claims`
list and its own `reasoning` field aren't being generated/validated for mutual consistency), or
simply underlying LLM unreliability on this specific model — needs investigation before assuming
either.

## Acceptance Criteria

- [x] Reproduce: **scope-adjusted, not done** — a statistically meaningful reproduction run (many
      live LLM calls, real cost/time) wasn't justified once the code-level root cause below was
      found and a defensive fix was possible regardless of exact frequency; not characterized
- [x] Investigate `verify_answer()`'s prompt/schema (`app/agents/` — wherever `VerificationResult`
      is produced) for whether `reasoning` and `unsupported_claims` are generated independently
      (allowing drift) or as a single coherent structured output — **confirmed a single call**:
      `verify_answer()` builds one `Agent(model, output_type=VerificationResult, ...)` and makes
      exactly one `agent.run(prompt)` — ruling out "two separate generations raced" as the
      mechanism
- [x] Root cause instead: `VerificationResult`'s field declaration order was `grounded`,
      `unsupported_claims`, `reasoning` — a tool-calling/structured-output model fills fields in
      schema order, so the verdict fields could get generated (and locked in) before the
      `reasoning` meant to justify them was even written
- [x] Fixed: reordered to `reasoning` first, and added an explicit prompt instruction that the
      three fields must agree with each other (see `AGT-043`'s commit) — not deferred as a known
      limitation, since the mechanism pointed to a concrete, low-risk fix (a field reorder no call
      site depended on positionally)
- [x] Decided: worth fixing now, not tracking as an unfixable limitation — done

## Notes

Not urgent/blocking — the overall Verifier behavior across both rounds of the real trace is
reasonable, not indiscriminately rejecting everything. This is one specific inconsistency worth
tracking, not evidence the Verifier is broken.

## Resolution (2026-10-05)

Fixed in `app/agents/schemas.py`'s `VerificationResult` (field order: `reasoning`, `grounded`,
`unsupported_claims` — `reasoning` first) and `app/agents/verifier.py`'s system prompt (explicit
"the three fields must agree" instruction). All existing call sites use keyword arguments, so the
reorder was a safe, non-breaking change — confirmed by running the full relevant test suite
(`test_schemas.py`, `test_verifier.py`, `test_build.py`, `test_end_to_end.py`, 20/20 passed)
before and after.

**Not independently re-verified live against a fresh contradiction** — the mechanism (schema
field order controlling generation order in structured/tool-call output) is well-understood and
the fix is low-risk regardless, but confirming the exact failure mode is gone would need another
real rejection with the new field order to inspect, which wasn't deliberately reproduced (see the
scope-adjusted acceptance criterion above). A live agentic run during `AGT-041`'s verification did
produce a `grounded: true` result with coherent reasoning/claims agreement, but that case wasn't
the rejection path most likely to exercise this specific bug. Worth a specific check next time a
real rejection happens to occur.
