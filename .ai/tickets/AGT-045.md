# AGT-045 — Mode Switch Leaves the Other Mode's Stale Result On Screen

Status: Done
Depends On: None
Category: Bug

## Description

Found 2026-10-05 from live screenshots: asked a question in Agentic RAG, got a real synthesized
answer. Switched to the Direct RAG tab *without asking a new question* -- the result panel kept
showing the old Agentic answer, still badged "Agentic RAG". From the screenshot alone this reads
as "Direct RAG returned the exact same synthesized answer as Agentic RAG", which defeats the
entire point of the comparison tool (Direct RAG never synthesizes anything -- it returns one raw
chunk verbatim, confirmed in `app/agents/direct_query.py`). The backends behave correctly and
differently; the frontend is just showing you last mode's leftover output under the new tab.

Root cause confirmed in `QueryPage.tsx`: the mode-toggle `onClick={() => setMode(m)}` only calls
`setMode` -- nothing clears `result`, `error`, or `selectedHistoryId`.

## Acceptance Criteria

- [x] Switching the mode tab clears the currently displayed result (and any error, and any
      selected-history-entry highlight) -- the result panel is empty until a new question is
      asked in the newly selected mode, never a leftover answer badged with the mode you just
      left
- [x] Reopening a history entry (`AGT-040`) still works as before -- clicking a past entry shows
      *that* entry's own mode/result, this fix only targets the tab-switch case
- [x] Deployed; verified by code review + build (no browser tool this session to physically click
      through -- see Resolution)

## Notes

One-line fix in `QueryPage.tsx`'s mode-toggle `onClick` handler (`setResult(null)`,
`setError(null)`, `setSelectedHistoryId(null)` alongside `setMode(m)`) -- the smallest, most
urgent fix in this batch since it actively misrepresents what the two modes do.

## Resolution (2026-10-05)

New `handleModeChange(newMode)` wraps `setMode` with `setResult(null)`/`setError(null)`/
`setSelectedHistoryId(null)`; the tab buttons call it instead of `setMode` directly. Deployed as
part of commit `1a5631c` on `main`; build/typecheck clean. Not physically click-tested in a real
browser (no browser tool this session) -- verified by code review that the handler is wired
correctly, not by an actual tab-switch-then-look.
