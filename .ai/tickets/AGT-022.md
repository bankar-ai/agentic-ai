# AGT-022 — Service Status Probe + Query Outcome/Retry Metrics

Status: Done
Depends On: AGT-021
Category: Improvement

## Description

Comparing `agentic-ai`'s dashboard against `enterprise-rag-platform`'s own surfaced two real gaps,
plus a broader "what should a multi-agent system actually track" pass (researched against current
practice: Galileo's multi-agent observability framework, OpenTelemetry's GenAI semantic
conventions, general agent-observability writeups):

1. **No service-status probe at all.** `self-hosted-rag-platform` has Grafana Cloud Synthetic
   Monitoring checks (`vm-app-health`, `cloud-run-docling-health`, `modal-ollama-health`) feeding
   its dashboard's "Service up/down" panel. `agentic-ai` has none — scale-to-zero makes this worse
   than it sounds, since a cold-start failure or a 5xx would currently go unnoticed unless someone
   happens to be querying it live.
2. **No request/error-rate counters.** `AGT-021` added *duration* histograms (per-node,
   `llm_generation_duration_seconds`), but nothing counts outcomes — there's no way to ask "how
   many queries failed today" or "what's the refusal rate" without reading raw logs/traces one at
   a time.
3. **No retry-loop visibility as a metric.** The Verifier→Research retry loop
   (`app/graph/build.py`'s `route_after_verifier`) is real, bounded, and already visible per-query
   in Langfuse traces, but not aggregated anywhere — "are we retrying a lot lately" isn't
   answerable from the dashboard.

**Explicit scope boundary:** this is observability only, same as `AGT-021` — no behavior change to
the graph, retry logic, or refusal logic. Retrieval-quality/groundedness-rate metrics are
deliberately out of scope here: `agentic-ai` doesn't own retrieval quality (that's
`enterprise-rag-platform`'s ERP-087), and groundedness is already a per-query Langfuse event
(`verification.grounded`) — aggregating that into a dashboard metric is a separate, smaller
follow-up if ever wanted, not bundled into this ticket.

## Acceptance Criteria

- [x] `GET /health` added to `agentic-ai` (no auth, no LLM/RAG-platform calls — must stay cheap
      enough to probe every 5 minutes without burning OpenRouter/RAG-platform quota)
- [x] A new Grafana Cloud Synthetic Monitoring check against that endpoint, mirroring
      `vm-app-health`'s shape (5-minute frequency, 10s timeout, `validStatusCodes: [200]`)
- [x] A query-outcome counter (`agentic_ai_query_outcome_total`, labeled `outcome` ∈
      `completed`/`refused`/`error`) incremented exactly once per `/query` call, in
      `app/api/router.py`'s `_event_stream` — on every exit path (the three existing `except`
      blocks plus the normal completion path), not just the happy path
- [x] A verifier-retry histogram (`agentic_ai_verifier_retry_count`) recording
      `final_state["retry_count"]` whenever a query reaches a result (completed or refused)
- [x] New dashboard panels on `agentic-ai -- Service Observability`: service up/down (reusing the
      existing "Service up/down" stat-panel pattern), query outcome rate, verifier retry count
- [x] Live-verified via direct Prometheus queries (and the render API for the dashboard panels) —
      same standard as `AGT-021`. The error-outcome counter was verified immediately without
      waiting on OpenRouter's quota reset, since the live query sent during verification already
      exercised an `except` path (`RagPlatformAuthError`, an expired test-session token — a
      different failure than `AGT-021`'s OpenRouter issue, equally valid for exercising this
      metric)
- [x] `gcp-deployment-tracker.md` updated

## Resolution (2026-10-04)

Deployed as revision `agentic-ai-00020-9d6`. Live-verified via direct Prometheus/API queries, not
inferred:

- `probe_success{job="agentic-ai-health"}` = `1` (Mumbai probe) — the new Synthetic Monitoring
  check (id `4548`, 5-minute frequency) is live and green.
- `agentic_ai_query_outcome_total{outcome="error"}` = `1` — recorded correctly from a real failed
  live query.
- `agentic_ai_verifier_retry_count` — closed out fully later the same day (see `AGT-021`'s "Final
  Verification" addendum): after switching the primary model to `google/gemma-3-27b-it`, a real
  query completed end-to-end and `agentic_ai_verifier_retry_count_count` = `1` landed.
- All three new dashboard panels confirmed via the render API: "Service up/down" shows a green
  UP, "Query outcome rate" now shows both `error` and `completed` data points, "Verifier retry
  count" has real data.

A real deployment-config bug was found and fixed along the way, not part of this ticket's own
scope but blocking it: an earlier redeploy attempt (during `AGT-021`'s follow-up) left the Cloud
Run service's env-var template pointing `OTEL_EXPORTER_OTLP_HEADERS` at a Secret Manager secret
that was never created, and had dropped the `LANGFUSE_*` vars entirely (a `--set-env-vars`/
`--set-secrets` combination replaces the whole set rather than merging). Fixed via
`gcloud run services update --remove-secrets=... --update-env-vars=... --update-secrets=...`,
restoring the exact original config; verified via `gcloud run services describe` before
redeploying `AGT-022`'s actual code.
