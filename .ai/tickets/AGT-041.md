# AGT-041 — Server-Side Query Cache + Durable History Database

Status: Done
Depends On: None
Category: Feature

## Description

`agentic-ai` has deliberately had no database of its own (`AGT-024`-era scope call — client-side
`localStorage` only). The project owner now wants two related capabilities that both need one:

1. **Query caching**: a repeat question (same user, same mode, same text) should return the
   stored answer instantly instead of re-running the pipeline — ~100s and real LLM cost for a
   full Agentic run, so this matters most there, but applies to both modes per 2026-10-04
   discussion.
2. **Durable history**: every query (not just the 5 the frontend shows) persisted server-side as
   an audit log, independent of any one browser's `localStorage`. No "browse older history" UI for
   now — audit-log-only scope, deliberately smaller; a browsing UI can be a later ticket if wanted.

**Approved approach** (brainstormed and approved 2026-10-04, written up here so the design isn't
lost before this ticket is picked up): one new dedicated Postgres instance (own Neon free-tier
project, not reusing `enterprise-rag-platform`'s — keeps data ownership boundaries clean, matches
the portfolio's per-project-owns-its-data pattern). One table, `query_history`, doing double duty
as both the audit log and the cache lookup: owner user id, mode, normalized question text, answer,
trace JSON, `duration_seconds`, timestamp. A cache hit is "a non-refused row exists for this
user+mode+normalized-question within the last 24h" -> return its stored answer/trace, record the
result as served-from-cache (near-zero duration), skip the pipeline entirely.

This is architectural (new subsystem: new database, new credentials, new backend read/write path,
cache-hit semantics) — needs its own spec via `superpowers:brainstorming`'s architectural path
before an implementation plan, not folded into the `AGT-037`-`040` UI tickets.

## Resolution (2026-10-04)

Implemented as `app/core/query_cache.py` (new module): `QueryCache` wraps an `asyncpg.Pool`,
`normalize_question` (case/whitespace-insensitive dedup key), `decode_user_id` (unverified JWT
`sub` claim decode -- never an auth decision, only a cache/history grouping key, since
`enterprise-rag-platform` already validated the token). `get_query_cache(database_url)` lazily
creates the pool and runs the table's `CREATE TABLE IF NOT EXISTS` on first real use, returning
`None` when `DATABASE_URL` is unset so an unconfigured deploy is unaffected. Wired into both
`/query` (checked at the top of `_event_stream`, replaying the stored trace as SSE `step` events
on a hit) and `/query/direct`.

**Neon project**: created by the project owner via console.neon.tech (`agentic-ai` project,
Postgres 18, AWS US East 2 Ohio -- same region as, but a separate project from,
`enterprise-rag-platform`'s own Neon database). Connection string stored in Secret Manager as
`agentic-ai-database-url`, Cloud Run service account granted `secretAccessor`, deployed via
`gcloud run deploy agentic-ai --source . --update-secrets=DATABASE_URL=agentic-ai-database-url:latest`
(revision `agentic-ai-00035-5kq`).

**Live-verified end to end** against the real account: `/query/direct` asked twice --
`duration_seconds: 1.4394436420000005` (real retrieval) then `0.0` (cache hit, identical answer).
The full agentic `/query` asked twice -- `duration_seconds: 47.968144573000004` (real pipeline,
`web_fallback` route, grounded verdict) then `0.0` with the complete original trace replayed as
real SSE `step` events, identical final answer. Case/whitespace variation
(`"  WHAT is the 75 degree   angle ladder rule?  "` vs. the original phrasing) also hit the cache,
confirming `normalize_question`. Queried the live Neon database directly and confirmed three real
rows: one `served_from_cache: false` (the original computation) followed by two
`served_from_cache: true` rows (the cache hits), all correctly scoped to the real decoded
`user_id` -- the audit-log half of this table's double duty, confirmed working exactly as
designed, not just the cache-speed half.
