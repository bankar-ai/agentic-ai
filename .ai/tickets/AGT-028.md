# AGT-028 — Content-Security-Policy and Security Headers

Status: In Progress
Depends On: None
Category: Security

## Description

Investigated the session-token/XSS question the project owner raised: the frontend's access
token necessarily lives in JS-readable memory (cross-origin constraint, can't use `enterprise-
rag-platform`'s httpOnly cookies directly — see `AGT-026`'s own notes). The one concrete defense-
in-depth mitigation available without a backend redesign is a strict CSP, so that even if a
dependency vulnerability or unsanitized render ever introduced an XSS primitive, it would have
nowhere to load/execute a payload from.

## Acceptance Criteria

- [x] `frontend/vercel.json`: strict `Content-Security-Policy` (`default-src 'self'`, no
      `'unsafe-inline'`/`'unsafe-eval'` — confirmed safe since the production Vite build has no
      inline scripts/styles), `connect-src` scoped to `'self'` plus the Cloud Run backend origin
      explicitly (required since the frontend calls that origin cross-origin)
- [x] `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
      `Referrer-Policy: strict-origin-when-cross-origin` added alongside it
- [x] Verified locally: `tsc -b && vite build` and `oxlint` both clean, no inline
      scripts/styles in the built output to violate the policy
- [ ] Live-verified: headers present on the deployed site, app still functions (login, query,
      documents panel) with the policy active — a CSP violation would show as a browser console
      error and a broken feature, not a server-side failure
