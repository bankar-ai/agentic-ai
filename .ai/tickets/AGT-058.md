# AGT-058 — Per-User Rate Limiting on Query Endpoints

Status: Backlog
Depends On: AGT-041
Category: Feature

## Description

Raised 2026-10-05 answering "are we checking for abusive usage of the tool?" -- confirmed by code
audit: no. No per-user rate limiting, request throttling, or usage quota exists at the application
level. Any authenticated user can call `/query`/`/query/direct` as fast and as often as they want.
Cloud Run's own `--max-instances 3` is an infra cost-control cap, not an abuse guardrail, and the
`AGT-031` OpenRouter budget gauges are observability only -- they report remaining credits, they
don't block anything.

## Acceptance Criteria

- [ ] Per-user rate limit on `/query` and `/query/direct` (the LLM/retrieval-calling endpoints --
      the ones actual abuse would target), backed by the existing Neon Postgres (`AGT-041`'s
      shared pool, `app/core/db.py`) so it's correct across Cloud Run's multiple instances, not an
      in-memory counter that would miss requests landing on a different instance
- [ ] A specific, documented limit (e.g. N requests per M minutes per user) -- reasonable default
      for a demo-scale app, adjustable later if too strict/loose in practice
- [ ] Over the limit: `429 Too Many Requests` with a clear message, not a silent failure or a
      generic 500
- [ ] Tests: under the limit succeeds, over the limit is rejected, the window resets correctly
- [ ] Deployed and verified

## Notes

Scoped to the two expensive endpoints, not `/documents`/`/history` (cheap, not the abuse surface
here). A simple fixed-window counter is enough for this scale -- no need for a more sophisticated
sliding-window/token-bucket algorithm given the traffic this app actually sees.
