# AGT-031 — Live OpenRouter Account Budget on the Dashboard

Status: Done
Depends On: None
Category: Improvement

## Description

The project owner wanted the *live, authoritative* shared $5 OpenRouter account balance visible
on the dashboard, not something they have to ask for and get a manually-checked number back.

## Acceptance Criteria

- [x] `app/core/openrouter_budget.py`: `maybe_record_openrouter_budget()` calls OpenRouter's own
      `GET /api/v1/credits` (the real billing source, same one checked manually all session) and
      records `agentic_ai_openrouter_account_total_credits_usd`/
      `agentic_ai_openrouter_account_total_usage_usd` gauges
- [x] Throttled to at most once per 10 minutes (a live number, not a real-time one) and piggybacked
      on real query traffic as a fire-and-forget background task — no new scheduler, and `/health`
      stays free of external dependencies (its own AGT-022 design)
- [x] Never affects the query it rode in on: wrapped in try/except, 5s timeout, failure just logs
- [x] New dashboard panels: live remaining budget, credits vs. usage
- [x] Deployed and live-verified

## Resolution (2026-10-04)

Shipped, but took four real bugs to actually work — each one found and fixed with live evidence,
not guessed at:

1. **`asyncio.create_task()` had no guaranteed owner.** A bare task created inside a request
   handler with nothing holding a reference to it can be cancelled or garbage-collected before it
   runs. Switched to a proper Starlette `BackgroundTask` tied to the response.
2. **`StreamingResponse(background=...)` still never ran.** Confirmed via Starlette's own source
   that `background` fires in the same `__call__` coroutine right after the stream finishes — but
   this Cloud Run service runs under the *default* `cpu-throttling` setting (CPU not guaranteed
   once the HTTP response has finished sending), and the sandbox freezing CPU reliably won the
   race against the background task in practice. Switched to a plain inline `await` in the request
   handler instead — fine given the check is already throttled to once per 10 minutes.
3. **The real bug: a `time.monotonic()` sentinel reset on every cold start.** Even with the inline
   await, the check still silently skipped every time. Added temporary diagnostic logging and
   cross-checked it against **native GCP Cloud Logging** (bypassing this project's own documented
   OTLP-export flakiness, AGT-018/020) to rule out a lost-log-line false negative. Found the real
   cause: `time.monotonic()`'s reference epoch resets on every fresh container boot, so a cold
   container's `now` was itself only ~34 seconds — always less than the 600-second throttle window
   compared against a `0.0` default `_last_checked_at`, so the check "throttled" on literally every
   single cold start. Fixed by using `None` ("never checked") as the sentinel instead of `0.0`.
4. **The exact `unit="USD"` naming bug from `AGT-030`, repeated.** Once the HTTP call finally
   fired (confirmed `200 OK` via native logging), the gauges were *still* unqueryable under their
   intended names — the same OTel-to-Prometheus bridge quirk already found and fixed once earlier
   the same day for the cost counter, just not applied here too. Fixed by dropping the redundant
   `unit=` kwarg from both gauges.

**Live-verified after all four fixes**, deployed as `agentic-ai-00033-lzh`:
`agentic_ai_openrouter_account_total_credits_usd` = `5`,
`agentic_ai_openrouter_account_total_usage_usd` = `0.004040749`. Dashboard's "Remaining shared
budget" stat panel confirmed showing `$4.9960` via the render API.

## Notes

This is account-wide, not per-project — `enterprise-rag-platform`'s own key draws from the same
balance. Both projects' dashboards could show this same pair of gauges if ever wanted; only
`agentic-ai`'s own dashboard gets it for now since that's the only project this ticket touches.
