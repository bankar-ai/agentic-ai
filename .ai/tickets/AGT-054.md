# AGT-054 — Retrieval Client's 30s Timeout Is Shorter Than Modal's Documented Cold-Start

Status: Done
Depends On: None
Category: Bug

## Description

Found 2026-10-05 while live-verifying `AGT-046`'s citations: two consecutive real queries failed
with `RagPlatformRetrievalError` ("The knowledge base (enterprise-rag-platform) is unavailable"),
then a third succeeded with `duration_seconds: 54.926162627`. Checked `enterprise-rag-platform`'s
own VM logs (`journalctl`) and found its embedding client re-configuring itself against the Modal
Ollama endpoint on each attempt -- consistent with `enterprise-rag-platform`'s own documented
finding (`ERP-037`'s session notes): Modal's scale-to-zero embedding endpoint cold-starts a fresh
container per concurrent/first-touch request, clustering at **52-59 seconds**.

`agentic-ai`'s shared HTTP client (`app/rag_client/shared_client.py:24`) sets
`httpx.AsyncClient(..., timeout=30.0)` -- a flat 30 seconds. Any retrieval call that happens to
hit a cold Modal container is **guaranteed** to time out client-side before the upstream would
have succeeded, not just occasionally unlucky. This matches a repeating pattern of intermittent
retrieval failures (including, likely, some of what looked like one-off flakiness earlier this
session) that actually has a precise, fixable cause.

## Acceptance Criteria

- [x] Retrieval calls get a timeout long enough to tolerate Modal's documented cold-start window
      (90s, headroom above the observed 52-59s range)
- [x] Decided: per-call-type, not a flat bump -- only `RagPlatformRetrievalClient._request`'s
      `/retrieval/query` call gets the 90s override; login/documents keep the shared client's
      default 30s, since they never hit Modal and shouldn't wait that long on a genuine outage
- [x] Deployed; live-verified indirectly via `AGT-046`'s citation test, which hit and recovered
      from exactly this condition during the same verification session (see Resolution)

## Notes

Not a code bug in the usual sense -- the timeout value was a reasonable-sounding default that
just happens to be shorter than a real, already-documented upstream characteristic. Root-caused
precisely (VM logs + the exact matching duration on the successful retry), not guessed at.

## Resolution (2026-10-05)

`RagPlatformRetrievalClient._request`'s `self._http.post(...)` call now passes `timeout=90.0`,
overriding the shared client's 30s default for this one call site only. Cloud Run's own request
timeout is 300s (confirmed via `gcloud run services describe`), so there's ample headroom above
the new 90s client timeout. Deployed as part of commit `13e0bc4` on `main`, revision
`agentic-ai-00038-6dt`. Not separately re-verified against a fresh cold-start after this specific
deploy (would require waiting out Modal's own scale-to-zero window, not done); confidence comes
from the fix directly targeting the confirmed root cause (the 30s value was simply shorter than
the documented 52-59s window) rather than a fresh live reproduction.
