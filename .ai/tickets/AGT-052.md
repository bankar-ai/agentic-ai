# AGT-052 — Expired Session Surfaces as Generic "Query Failed (502)", Not "Please Log In Again"

Status: Backlog
Depends On: None
Category: Bug

## Description

Found 2026-10-05 from a live failure (screenshot: typed "hi" in Direct RAG, got "Query failed
(502)."). Traced to the actual root cause via `enterprise-rag-platform`'s own VM logs
(`journalctl -u rag-platform.service`), not assumed: at the exact failure timestamp, that
platform logged `POST /retrieval/query HTTP/1.1 401 Unauthorized` -- a real, specific rejection,
not a network/outage issue.

The full chain:

1. `StaticTokenAuth.refresh()` (`app/rag_client/auth.py:128`) already raises a clean, specific
   `RagPlatformAuthError("Supplied session expired or was rejected; please log in again.")` --
   this is deliberate, documented, correct behavior (a caller-supplied session has no password to
   silently refresh with).
2. But `app/api/router.py` catches `RagPlatformAuthError` in the *same* except clause as
   `RagPlatformRetrievalError`/`RagPlatformDocumentsError` (lines 164, 277, 333) and maps **both**
   to a generic `HTTPException(502, "enterprise-rag-platform is unavailable: ...")` -- losing the
   distinction between "the service is down" and "your session expired, log in again."
3. The frontend's expiry-handling (`AGT-026`) only ever checks `response.status === 401` (`api.ts`)
   or `err.message.includes("expired")` (`QueryPage.tsx`) -- neither matches a `502` with the
   message "enterprise-rag-platform is unavailable: Supplied session expired...", so the dedicated
   "save your draft, log out, redirect to login" flow never fires for this case. The user just
   sees an unhelpful generic failure and has no idea they need to log in again.

This affects all three endpoints that call into `enterprise-rag-platform` with a caller's own
session: `/query`, `/query/direct`, `/documents`.

## Acceptance Criteria

- [ ] Backend: `RagPlatformAuthError` is caught separately from `RagPlatformRetrievalError`/
      `RagPlatformDocumentsError` in all three endpoints, mapped to `401` (not `502`) with a clear
      "your session has expired, please log in again" detail message
- [ ] `/query`'s SSE `error` event distinguishes this case too (e.g. a distinct `type`, like
      `"SessionExpired"`), since it can't rely on an HTTP status code once the stream has already
      started with `200`
- [ ] Frontend: `runQuery`'s SSE error handling recognizes the distinct error type and throws
      something `QueryPage.tsx`'s existing expiry flow (draft-save, logout, redirect) already
      catches -- `runDirectQuery`/`fetchDocuments` should work automatically once the backend
      correctly returns `401` (both already check `response.status === 401`)
- [ ] Deployed and live-verified: force an expired/invalid token (e.g. wait out the 30-minute
      expiry, or use a deliberately stale token) and confirm the UI shows "please log in again"
      with draft preservation, not a generic "Query failed" error

## Notes

High-value fix: this doesn't just improve an error message, it makes `AGT-026`'s entire
expiry-handling feature actually fire for its main real-world trigger, which it currently never
does. Root-caused via `enterprise-rag-platform`'s own VM logs rather than guessed at -- this
project's established practice (see `AGT-031`/`AGT-032` for the same technique catching a
different bug).
