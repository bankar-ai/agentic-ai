# AGT-058 — Per-User Rate Limiting on Query Endpoints

Status: Done
Depends On: AGT-041
Category: Feature

## Description

Raised 2026-10-05 answering "are we checking for abusive usage of the tool?" -- confirmed by code
audit: no. No per-user rate limiting, request throttling, or usage quota exists at the application
level. Any authenticated user can call `/query`/`/query/direct` as fast and as often as they want.
Cloud Run's own `--max-instances 3` is an infra cost-control cap, not an abuse guardrail, and the
`AGT-031` OpenRouter budget gauges are observability only -- they report remaining credits, they
don't block anything.

## Acceptance Criteria

- [x] Per-user rate limit on `/query` and `/query/direct` (the LLM/retrieval-calling endpoints --
      the ones actual abuse would target), backed by the existing Neon Postgres (`AGT-041`'s
      shared pool, `app/core/db.py`) so it's correct across Cloud Run's multiple instances, not an
      in-memory counter that would miss requests landing on a different instance
- [x] A specific, documented limit: 20 requests per 10 minutes per user
- [x] Over the limit: `429 Too Many Requests` with a clear message
- [x] Tests: under the limit succeeds, over the limit is rejected (mocked); window-reset behavior
      covered by the SQL's own `created_at > cutoff` clause, not separately unit-tested (would
      need a real clock/DB) -- **live-verified instead**, see Resolution
- [x] Deployed and **live-verified against the real deployment**, see Resolution

## Notes

Scoped to the two expensive endpoints, not `/documents`/`/history` (cheap, not the abuse surface
here). A simple fixed-window counter is enough for this scale -- no need for a more sophisticated
sliding-window/token-bucket algorithm given the traffic this app actually sees.

## Resolution (2026-10-05)

New `rate_limit_events` table + `RateLimiter.check_and_record`, checked before the cache lookup,
OpenRouter budget check, or graph construction in both endpoints -- an over-limit request costs
nothing beyond one cheap `SELECT count(*)`. Deployed as part of commit `fdbb912` on `main`,
revision `agentic-ai-00041-gg6`.

**Live-verified with a real burst against the production deployment**: fired 25 rapid real
requests at `/query/direct` with the real account. Requests 1-19 succeeded (`200`), request 20
onward returned `429` with `"Too many requests -- please slow down and try again shortly."` --
the limit fired at exactly the configured threshold (some of the 20-count had already accumulated
from earlier testing in the same session, confirmed by querying `rate_limit_events` directly:
20 real rows for the account in the live window). Not an estimate or a mocked test -- the real
endpoint, the real database, the real threshold.
