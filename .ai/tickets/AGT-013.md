# AGT-013 — Multi-Tenant Auth: Per-User RAG-Platform Tokens End-to-End

Status: Done
Depends On: None
Category: Improvement

## Description

Today `agentic-ai` is single-tenant: every query, from every visitor, uses one fixed service
account (`agentic-ai-service@example.com`) baked into `.env`, so everyone sees the same documents
regardless of who's asking. This surfaced as a real gap: there's no end-user login concept at all,
and reusing `enterprise-rag-platform`'s own login (rather than building a second identity system)
is both the simplest and most honest design — `agentic-ai` never owns passwords, it only forwards
an already-issued RAG-platform access token.

**Additive, not a breaking change**: when no token is supplied, behavior is unchanged (the fixed
service account still works, so local dev / CI / the existing smoke-test flow keep working as-is).

The identity has to flow further than just the API layer: Gatekeeper's exploratory search *and*
Research's MCP subprocess call both hit the RAG platform's retrieval API, and both need to act as
the calling user, not the fixed service account, for multi-tenancy to be real rather than
cosmetic.

## Acceptance Criteria

- [x] `POST /query` accepts an optional `Authorization: Bearer <token>` header
      (`extract_bearer_token` in `app/api/router.py`)
- [x] A new lightweight auth adapter (`StaticTokenAuth`, `app/rag_client/auth.py`) wraps an
      already-issued access token, satisfying a new `RagPlatformAuthProvider` Protocol both it and
      `RagPlatformAuth` implement — `RagPlatformRetrievalClient` no longer needs to know which one
      it was given. `refresh()` raises `RagPlatformAuthError` (no password to recover with), which
      the existing router error handling already turns into a clear `event: error`, not a graph crash
- [x] `get_graph(user_token)` builds its retrieval client from the per-request token when present,
      the configured service account when absent
- [x] The MCP subprocess receives the active identity per-call: `research.py`'s
      `_mcp_subprocess_env` forwards `RAG_PLATFORM_ACCESS_TOKEN` when a user token is present,
      and `mcp_server/server.py`'s new `_build_auth` prioritizes it over the fixed service account
- [x] Gatekeeper's exploratory search uses the same per-request `retrieval_client` `get_graph()`
      built — no separate configuration path, so both retrieval calls for one query see the same
      user's documents
- [x] Tests: 16 new tests covering the unauthenticated-unchanged path, genuine per-request token
      usage (not ignored), and clean error surfacing — plus **live-verified against the real
      `enterprise-rag-platform` deployment** (not just mocks): a real user-supplied token
      successfully retrieved real content; a bad token cleanly raised `RagPlatformAuthError`
      rather than crashing
