# AGT-021 — Per-Node Latency Instrumentation (Gatekeeper/Research/Writer/Verifier + MCP + LLM)

Status: Backlog
Depends On: None
Category: Improvement

## Description

The Grafana dashboard restructure (2026-10-04) moved `enterprise-rag-platform`-specific latency
panels (LLM generation duration, RAG pipeline stage latency, ingestion duration) off the shared
dashboard because `agentic-ai` has no equivalent instrumentation of its own — those panels showed
"No data" for `agentic-ai` correctly, not as a bug, but because nothing in this codebase ever
emits spans or metrics under those names. This ticket is the actual equivalent: real latency
visibility into `agentic-ai`'s own pipeline (Gatekeeper → Research → Writer → Verifier, the MCP
tool-call round trip, the LLM call itself).

**Explicit scope boundary, agreed with the project owner:** this is latency/performance data
only. `app/core/tracing.py`'s `LangfuseTracer.trace_step()` already sends each node's *semantic*
content (route, reasoning, draft text, evidence count, grounded verdict) to Langfuse on every
live query — real, working, already deployed. `create_event()` is a point-in-time marker with no
span duration, so Langfuse currently has zero visibility into how long anything actually took.
This ticket fills exactly that gap and nothing else — no re-sending of content Langfuse already
has, no new Langfuse integration work.

## Acceptance Criteria

- [ ] `app/graph/build.py`'s four node functions (`gatekeeper_node`, `research_node`,
      `writer_node`, `verifier_node`) wrapped in real OTel spans with actual start/end timing —
      verify the exact `tracer.start_as_current_span(...)` API against the installed
      `opentelemetry-sdk` before writing code, don't assume the pattern from memory
- [ ] The MCP tool-call round trip (`app/agents/research.py`'s `_research_kb`, the
      `direct_call_tool` call specifically) gets its own child span, distinguishable from the
      rest of `research_node`'s work (so "how long did Research spend waiting on
      `enterprise-rag-platform` via MCP" is answerable on its own, not blended into Gatekeeper's
      exploratory-search time or the rest of Research)
- [ ] A custom histogram metric mirroring `enterprise-rag-platform`'s own
      `llm_generation_duration_seconds` naming convention (same metric name, so the existing
      "LLM generation duration" panel on the ERP detail dashboard could in principle show either
      project's data if ever reused that way) — populated around each PydanticAI `agent.run()`
      call in `app/agents/gatekeeper.py`/`writer.py`/`verifier.py`
- [ ] New Grafana panels for this (reuse the existing "Latency Breakdown" pattern/naming) —
      decide placement with the project owner: back on the shared dashboard (now that they'd
      show real `agentic-ai` data, unlike before) vs. a dedicated `agentic-ai` detail dashboard
      mirroring `enterprise-rag-platform -- Service Detail`'s shape
- [ ] Live-verified via direct Tempo/Prometheus API queries (same standard this project has held
      all session) that real per-node, per-MCP-call, and per-LLM-call durations actually arrive
      for a live query — not inferred from the absence of errors
- [ ] `gcp-deployment-tracker.md` updated

## Notes

Not a correctness issue, not blocking anything — purely closing an observability gap the project
owner noticed by comparing `agentic-ai`'s dashboard view against `enterprise-rag-platform`'s own.
