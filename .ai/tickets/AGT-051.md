# AGT-051 — Revisit Persistent Sessions / Refresh Tokens Now That a Database Exists

Status: Done
Depends On: AGT-041
Category: Feature

## Description

The "session will expire soon" warning (`AGT-026`) exists because `agentic-ai` deliberately has
no server-side session storage: `StaticTokenAuth` holds only the short-lived access/CSRF tokens
`enterprise-rag-platform` issues at login, with no way to silently refresh them. `AGT-013`/`AGT-026`
investigated true silent refresh and explicitly declined it: *"can't be done without a real
architecture change -- `agentic-ai`'s backend would have to start holding per-user refresh-token
state it doesn't have today."*

That blocker no longer fully applies. `AGT-041` gave `agentic-ai` its first real database
(dedicated Neon Postgres). Storing a refresh token server-side, scoped per user, is now a much
smaller lift than it was when "stand up a database just for this" was the alternative being
weighed against "live with the warning." Worth re-evaluating, not assuming the old answer still
holds now that the premise it was based on has changed.

**Not a bug** -- the current warning-plus-draft-preservation behavior is a previously made,
reasoned decision, not an oversight. This ticket is "should we revisit it," not "this is broken."

## Resolution (2026-10-05) -- investigation complete, implementation deliberately not started

**Confirmed feasible, with specifics.** Read `enterprise-rag-platform`'s own `app/auth/router.py`
and `app/auth/schemas.py` directly:

- `POST /auth/login` there sets **both** `access_token` and `refresh_token` as `httpOnly` cookies
  (`set_auth_cookies`) and returns only `user_id`/`csrf_token` in the JSON body -- `httpOnly` only
  blocks *browser* JavaScript from reading a cookie; it does nothing to stop a server-side HTTP
  client (like `agentic-ai`'s own `httpx.AsyncClient`) from reading the `Set-Cookie` response
  header directly. The refresh token is not secret from `agentic-ai`'s backend -- it's sitting
  right there in the response.
- `agentic-ai` already proves this works: `app/rag_client/auth.py`'s `RagPlatformAuth` (used by
  the Gradio UI's own login and the MCP server) already does real silent refresh today, exactly
  this way -- it logs in, lets its `http_client`'s cookie jar hold the `refresh_token` cookie
  automatically, and later calls `POST /auth/refresh` relying on that same jar to resend it. This
  already works, right now, for that one flow.
- The gap is specifically in `app/api/auth.py`'s `POST /auth/login` (the proxy the browser SPA
  calls): it opens a **fresh, short-lived** `httpx.AsyncClient` per login request
  (`async with httpx.AsyncClient(...) as http_client:`), which captures the `refresh_token`
  cookie during `login_and_extract_session` -- then discards it the moment the `async with` block
  exits, a few lines later. Nothing ever reads `http_client.cookies.get("refresh_token")` before
  it's gone. `StaticTokenAuth` (what every subsequent per-user request actually uses) was never
  designed to hold one at all.

**So the original `AGT-026` blocker is gone, confirmed, not just "probably."** The remaining work
is real but mechanical: capture the refresh token in `/auth/login`, store it server-side keyed by
the already-available decoded user id (`app/core/query_cache.py`'s `decode_user_id`, reusable
as-is), and build a refresh-then-retry path.

**Why this ticket stops at "recommended" rather than building it:** there's a real question the
investigation surfaced that wasn't asked before -- should `agentic-ai` hold another platform's
refresh token in its own database at all? It's technically *obtainable*, but obtainable isn't the
same as *appropriate*: a stored refresh token is a longer-lived credential than anything
`agentic-ai` has ever held, and it's not this project's own credential to begin with. That's a
trust-model/security-posture decision, not an engineering one -- worth the project owner's
explicit "yes, build this" before writing a spec, not something to default into because the
technical path turned out to be open.

**Recommendation if approved:** store the refresh token in the existing `AGT-041` Neon database
(new table, not reusing `query_history`), refresh-then-retry in `StaticTokenAuth`'s existing
`refresh()` seam (currently hardcoded to fail), and propagate any rotated access/csrf token back
to the frontend via response headers so its held session stays in sync without the user noticing
anything happened.

## Implementation (2026-10-05, approved same day)

Built almost exactly as recommended, with one simplification: rotated tokens are **not**
propagated back to the frontend. Each request's own `StaticTokenAuth` self-heals via the stored
refresh token on a `401`, so the frontend's held (now-stale) access token simply becomes
irrelevant once it expires -- every subsequent request transparently re-refreshes server-side
using the database-stored refresh token instead. Functionally equivalent for the user (no "log in
again" prompt ever appears while the refresh token stays valid), at the cost of one extra
`/auth/refresh` round trip per request after the original access token expires, rather than zero
extra round trips if the frontend held a freshly-rotated token. Accepted as the simpler design;
revisit only if that extra round trip is ever measured to matter.

New `app/core/db.py` (shared pool, `query_cache.py` refactored to use it too -- one Neon
connection pool per process, not one per table) and `app/core/session_store.py`
(`user_sessions` table, separate from `query_history` since a refresh token is a materially
different kind of data). `POST /auth/login` (`app/api/auth.py`) now captures the `refresh_token`
`Set-Cookie` and stores it (best-effort, never blocks login). `StaticTokenAuth.refresh()`
(`app/rag_client/auth.py`) attempts a real refresh via the stored token first, rotating and
re-saving it on success, deleting it if the platform rejects it. Wired into all three
`router.py` endpoints **and** the MCP subprocess (`app/mcp_server/server.py`, `_build_auth`/
`_get_retrieval_client` made async; `DATABASE_URL` now forwarded via
`app/agents/research.py`'s `_FORWARDED_ENV_PREFIXES`) -- the `kb` route is the dominant real
retrieval path, so leaving it out would have under-delivered on the actual goal. The Gradio demo
(`app/ui/app.py`) was left unwired (out of scope, not the deployed production path).

New/updated tests: `tests/core/test_session_store.py` (new), `tests/rag_client/test_auth.py`
(5 new silent-refresh cases: no stored token, successful refresh, rotation, dead-token cleanup),
`tests/mcp_server/test_server.py` (updated for the async signatures), `tests/api/test_auth.py`
(2 new: storage succeeds, storage failure doesn't break login), `tests/api/test_router.py`
(updated `get_graph` call-signature assertion). Full suite: 174 passed, same one pre-existing
unrelated `.env`-drift failure as every other ticket tonight.

**Live-verified end to end against the real deployment, rigorously, not just "it returned 200"**:
1. Fresh login confirmed storing a real refresh token (queried the live Neon table directly).
2. An access token from over an hour earlier in this session (confirmed genuinely expired/
   rejected -- a fresh question with it returned a real `401` from `enterprise-rag-platform`'s own
   `/retrieval/query`, confirmed via VM `journalctl`) was then reused with a **new, uncached**

3. VM logs show the complete real sequence: `POST /retrieval/query 401` -> `POST /auth/refresh
   200` -> embedding client call -> `POST /retrieval/query 200`, two seconds and ~48 seconds later
   respectively -- the exact mechanism working, not inferred from the outcome alone.
4. Confirmed token rotation: the stored `refresh_token` in the live table changed value and
   `updated_at` to a timestamp matching the `POST /auth/refresh` log line exactly, proving the
   rotate-and-resave path (not just the read path) works correctly too.
