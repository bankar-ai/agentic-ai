# AGT-035 — Verifier's Reasoning/Unsupported-Claims Never Traced

Status: Done
Depends On: None
Category: Bug

## Description

Found live (2026-10-04) digging into why a real `kb`-route query was refused:
`app/graph/build.py`'s `verifier_node` only keeps `{"agent": "verifier", "grounded":
verification.grounded}` in the traced step — `verification.reasoning` and
`verification.unsupported_claims` (both real fields on `VerificationResult`, computed by
`verify_answer()`) are discarded immediately after. Not saved to Langfuse, not logged, not
returned in the `/query` SSE response. A real rejection is completely undebuggable after the fact
— confirmed live: even with full Langfuse API access (`fields=core,basic,io,metadata`), the detail
genuinely isn't there, because it was never sent.

Gatekeeper's own step already includes `reasoning` (`{"agent": "gatekeeper", "route": ...,
"reasoning": decision.reasoning}`) — Verifier should match that pattern.

## Acceptance Criteria

- [x] `verifier_node`'s traced step includes `reasoning` and `unsupported_claims` alongside
      `grounded`
- [x] This automatically also reaches the frontend's "Agent trace" panel (it already renders
      `JSON.stringify(step)` per trace entry) and Langfuse (via the existing `trace_step` call) —
      no separate wiring needed in either place
- [x] Deployed and live-verified: a real rejected query shows its actual reasoning, not just
      `grounded: false`

## Resolution (2026-10-04)

Deployed as revision `agentic-ai-00034-stp`. Live-verified with a real rejected query against the
project owner's own account -- the traced step now shows full detail, e.g.: `"reasoning": "While
the evidence mentions training on fall protection and using correct anchorage, it does not
explicitly state that workers should be trained to identify, understand, and control fall
hazards..."`, `"unsupported_claims": ["Workers should be trained to identify, understand, and
control fall hazards.", "Use correct anchorage for fall arrest systems."]`. This also surfaced a
genuinely interesting, previously invisible pattern: the Verifier is catching a subtle distinction
between a source *recommending* something and a draft stating it as *already being done* --
exactly the kind of nuance this ticket's fix was meant to make visible, not something that could
have been confirmed from `grounded: false` alone.

**Re-verified 2026-10-04, later same day**, with a fresh real account login and a new prompt
deliberately phrased to invite exactly this failure mode ("Describe exactly what workers at this
company are trained to do regarding fall hazards, as already implemented."): the pipeline rejected
the draft twice in a row, and both traced `verifier` steps carried full `reasoning` and
`unsupported_claims`, e.g. round 1: `"reasoning": "The document explicitly states 'No fall
protection program'. However, the claim \"assign a person to inspect fall protection equipment
before each use\" is not directly supported by the provided evidence..."`,
`"unsupported_claims": ["However, the company currently has no fall protection program.", "assign
a person to inspect fall protection equipment before each use"]`; round 2 caught a different
unsupported claim after the Writer's rewrite. Confirms the fix holds across repeated runs, not
just the one query used for the original verification.
